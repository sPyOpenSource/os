Setup — the only boilerplate you need

import jx.zero.*;

static Naming      naming      = InitialNaming.getInitialNaming();

Every synchronization primitive in JCore arrives through one of these four names. If you remember nothing else from this page, remember that line.

AtomicVariable — your condition variable

Object get();
void   set(Object value);
void   blockIfEqual(Object testValue);      // park if value == test  → use for wait()
void   blockIfNotEqual(Object testValue);   // park if value != test
void   atomicUpdateUnblock(Object v, CPUState s);  // set + wake  → use for notify()
void   activateListMode();                  // allow MANY waiters, wake all on change
Java you knowJCore equivalent
wait()av.blockIfEqual(null)
notify()av.atomicUpdateUnblock(newValue, consumerState)
notifyAll()call av.activateListMode() first
synchronized(x)jx.synch.mutex.BlockingLockImpl
No monitor, no ownership. Unlike Java's wait(), JCore's blockIfEqual does not require holding a lock, and there is no lock to hold. Atomicity comes from DISABLE_IRQ inside the native call, not from the caller.

The three canonical patterns

1. Mutual exclusion

scheduler.disableThreadSwitching();
  // critical section — must be a few instructions, no blocking, no allocation
scheduler.enableThreadSwitching();

2. Blocking hand-off (lock-free queue)

src/jx/synch/blocking/Queue.java — each link is an AtomicVariable:

enqueue:  node.next.set(null);
          tail.next.atomicUpdateUnblock(node, consumer);
dequeue:  head.next.blockIfEqual(null);
          head = (Node) head.next.get();

Set-and-wake in one call ⇒ no lost-wakeup window. Same trick as Massalin & Pu's synthesis-kernel HOOK, credited in the file header.

3. Lock-free list

src/jx/buffer/multithread/MultiThreadList.java — CAS loops over cpuManager.getCAS(...) for the structural updates, AtomicVariable in list mode to park consumers.

Known bug. CPUState.java:18 declares STATE_BLOCKEDUSER = 9, but the kernel has STATE_PORTAL_WAIT_FOR_RET = 9 and STATE_BLOCKEDUSER = 10 (src/Headers/core/thread.h:26–27). The constant points at the wrong state. Currently harmless — nothing in OS/src/ calls CPUState.getState() — but never write state == STATE_BLOCKEDUSER.

Glossary

Domain: JCore's unit of protection, memory, and scheduling. Owns its threads and type space. Avoid: process, address space

Portal: A typed, cross-domain reference that behaves like an RPC proxy. The only way domains communicate. Avoid: proxy, RPC stub

Domain-local scheduler: The per-domain level that picks among a domain's own threads. Fed by the global level. Avoid: local scheduler, second-level scheduler

Disable thread switching: Raising a barrier against preemption for the current thread. JCore's critical-section primitive. Avoid: disabling interrupts (broader — also stops IRQ handlers), locking

AtomicVariable: A one-slot condition variable. Test-and-park, or set-and-wake, atomically under DISABLE_IRQ. Avoid: atomic reference, lock

List mode: An AtomicVariable mode where many threads may park and all are woken by the next write. Avoid: broadcast mode

CPUState: A kernel handle identifying one thread. How you name yourself in order to block or be unblocked. Avoid: Thread object

Rule of thumb. On a single CPU with no priorities, every shared-mutable-state bug in JCore is a missing disableThreadSwitching() around a test-and-set, or an AtomicVariable used where a plain field was needed.

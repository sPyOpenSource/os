How Classes Are Loaded in JCore OS

Lesson 1 of the Java Internals series. Mission

When the JCore OS starts a Java program, it doesn't use a traditional JVM classloader. Instead, it uses a two-store architecture designed for AOT (Ahead-of-Time) compilation. This lesson traces the path from a ZIP archive to a parsed ClassData object.

The Players

FileRole
ClassManager.javaEntry point — orchestrates loading from ZIPs into two stores
ClassStore.javaHashtable-backed storage, keyed by internal class name
MemoryClassSource.javaAdapts kernel Memory to ClassData
ClassFinder.javaInterface: findClass(String name)
ClassData.javaThe parsed class — fields, methods, constant pool, etc.

The Flow

DomainStarter.createDomain()
  └─> ClassManager.addFromZip(domainZip, libZips)
        ├─ Iterate ZIP entries, filter by ".class"
        ├─ MemoryClassSource(memory) → ClassData(DataInput)
        │     └─ Read magic 0xCAFEBABE, version, constant pool,
        │        access flags, this/super, interfaces, fields, methods
        ├─ libClassStore.addClass(name, classData)
        └─ domClassStore.addClass(name, classData)

  findClass("java/lang/Object")
        └─ domClassStore.findClass() ?: libClassStore.findClass()

Step-by-Step

1. ZIP Iteration

ClassManager.addFromZip (src/jx/classstore/ClassManager.java:33) receives a domain ZIP and an array of library ZIPs, all as kernel Memory objects. It unpacks each ZIP using jx.zip.ZipFile, filtering entries whose name contains ".class".

Notice the split: library ZIPs and the domain ZIP are kept separate at line 54-55:

if (i==-1) domdata.addElement(entry.getData());
else libdata.addElement(entry.getData());

2. Memory → ClassData

Each class file's raw bytes (Memory) are wrapped by MemoryClassSource (src/jx/classstore/MemoryClassSource.java):

new DataInputStream(new MemoryInputStream(input))

This feeds into ClassData's constructor, which calls readFromClassFile() — a 50-line method that reads the entire binary classfile format sequentially.

3. Two Stores

ClassManager maintains two ClassStore instances (src/jx/classstore/ClassStore.java):

  • libClassStore — framework / library classes
  • domClassStore — application / domain classes

ClassStore is a thin wrapper around a Hashtable (keyed by internal class name like "java/lang/Object").

4. Class Lookup

findClass() (ClassManager.java:202) normalizes dots to slashes, then checks domClassStore first, falling back to libClassStore:

String className = classN.replace('.', '/');
ClassData cc = domClassStore.findClass(className);
if (cc == null) cc = libClassStore.findClass(className);
return cc;

5. Dependency Validation

After loading, computeClassGraph() (ClassManager.java:87) iterates every class's constant pool looking for ClassCPEntry references and throwErrors if any referenced class isn't found. This is an eager validation step — all dependencies must be resolvable at load time.

Key Architectural Decisions

DecisionWhy
Two stores instead of parent delegationClasses are loaded all at once for AOT compilation, not lazily at runtime
Memory → DataInputStream bridgeMemory is the kernel's native buffer type; DataInputStream is the standard Java parsing API
Dot-to-slash normalizationInternal class names use slashes (java/lang/Object); the ClassFinder interface accepts dotted names
Eager validationBetter to fail early at domain-creation time than at runtime

What's Missing?

This codebase has no interpreter. The parsed ClassData is not used by a runtime JVM — instead, it's fed to ByteCodeTranslater (in a separate compiler domain) which emits native code as a .jll file. The runtime uses VMClass handles (kernel objects), not ClassData.

Primary source: src/jx/classstore/ClassManager.java and the JVM Spec, Chapter 4 — The class File Format. Read them alongside this lesson.

Quiz

1. What interface does ClassManager implement?

Reveal answer

ClassFinder — provides findClass(String) for looking up classes by name.

2. When findClass("java.lang.Object") is called, which store is checked first?

Reveal answer

domClassStore — domain store is checked before lib store (ClassManager.java:204).

3. Why does MemoryClassSource exist?

Reveal answer

It bridges the kernel's Memory buffer type (raw bytes from ZIP archives) to Java's standard DataInputStream API that ClassData expects.

4. True or False: Classes are loaded lazily at runtime, like in a standard JVM.

Reveal answer

False. All classes are loaded eagerly at domain-creation time for AOT compilation.

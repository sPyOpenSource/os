32-bit vs 64-bit in JCore OS

Lesson 3 of the Java Internals series. Mission | Previous: JDK Reimplementation

The JVM specification defines type sizes once — they're the same on every architecture. But the runtime (JCore OS) must decide how big a reference actually is in memory. Right now, it's hardcoded to 32-bit.

The Hardcoded 32-bit: Line 123

Open src/jx/classfile/datatypes/BCBasicDatatype.java:117. The sizeInByte() method defines every type's size in bytes:

case INT:       return 4;
case LONG:      return 8;
case FLOAT:     return 4;
case DOUBLE:    return 8;
case REFERENCE: return 4;   // ← THIS LINE
case BYTE:      return 1;
case CHAR:      return 2;
case SHORT:     return 2;

Notice: int, long, float, double are all defined by the JVM spec and are the same everywhere. But REFERENCE is a runtime decision — on a 32-bit machine it's 4 bytes, on 64-bit it's 8.

And in BCReference.java, the reference value is stored as:

private int value;   // always 4 bytes — 32-bit assumption

Why This Matters

On a 64-bit ARM system (like your Apple Silicon Mac), each object reference would need 8 bytes instead of 4. That means:

  • Heap size — references double in size, so the same heap holds fewer objects
  • Alignment — 8-byte pointers need 8-byte alignment; the current 4-byte alignment would break
  • GC overhead — the garbage collector must scan 8-byte pointers instead of 4-byte
  • Memory layout — the ObjectDesc struct in the C kernel uses code_t *vtable (pointer) — this doubles in size on 64-bit

What the JVM Spec Says

The JVM Spec §2.3 defines these as architecture-independent:

  • byte: 8 bits, signed, two's complement
  • short: 16 bits, signed, two's complement
  • int: 32 bits, signed, two's complement
  • long: 64 bits, signed, two's complement
  • float: 32 bits, IEEE 754 single-precision
  • double: 64 bits, IEEE 754 double-precision
  • reference: an address that can point to a heap object (size depends on the implementation)

The classfile format itself stores constants at fixed sizes (int=4 bytes, long=8 bytes). References in constant pool entries are stored as 2-byte indices, not raw addresses — so the classfile format is portable across architectures.

The Build System Targets 32-bit

The kernel's Makefile (lib/jcore/Makefile:61) explicitly compiles for 32-bit:

CORECCFLAGS = ... -m32 -target i386-pc-linux-gnu ...
CORELDOPTS = -m elf_i386

And System.java reports itself as 32-bit x86:

properties.put("os.arch", "i586");

Quiz

1. Is the long type 8 bytes on 32-bit and 64-bit JVMs?

Reveal answer

Yes — long is always 8 bytes. Only reference size is architecture-dependent.

2. Where is the 32-bit reference assumption hardcoded in JCore?

Reveal answer

BCBasicDatatype.sizeInByte() at line 123: case REFERENCE: return 4;

3. Why doesn't the classfile format break when moving between 32-bit and 64-bit?

Reveal answer

Constant pool entries store indices, not raw addresses. Sizes like int=4, long=8 are fixed by the JVM spec.

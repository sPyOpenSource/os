Lesson 2: The Global Descriptor Table

How the CPU knows which segment is which

In Lesson 1, we saw the GDT in passing — four entries loaded by lgdt [ptrgdt] before switching to protected mode. In this lesson we decode exactly what those bytes mean, because the GDT is the nervous system of x86 protected mode. If PicOS ever needs a new segment descriptor (user-mode code, TSS, LDT), you need to understand this.

The Raw Bytes

Here's the GDT from bts_dsk.S, verbatim:

.align 4, 0x00
mygdt:
    .word 0x0000, 0x0000, 0x0000, 0x0000   # null descriptor
    .word 0xFFFF, 0x0000, 0x9A00, 0x00CF   # 4GB 32-bit code at 0x0
    .word 0xFFFF, 0x0000, 0x9200, 0x00CF   # 4GB 32-bit R/W at 0x0
    .word 0xFFFF, 0x0000, 0x9A06, 0x008F   # 4GB 16-bit code at 0x60000
endgdt:

Each .word is 2 bytes. Four of them per entry = 8 bytes per descriptor. Four entries = 32 bytes. Let's unpack entry #1 (the 32-bit code segment at selector 0x08):

+0FF FFSegment Limit [15:0] +200 00Base Address [15:0] +49ABase [23:16] + Access Byte +500Base [23:16] +6CFFlags + Limit [19:16] +700Base [31:24]

But wait — GAS's .word behaves the same in .code16 as in .code32: it always emits 2 bytes, low byte first (little-endian). So the sequence .word 0xFFFF, 0x0000, 0x9A00, 0x00CF produces the 8 bytes:

Offset:  0  1  2  3  4  5  6  7
         FF FF 00 00 00 9A CF 00
         ───── ───── ───── ─────
         .word .word .word .word
         0xFFFF 0x0000 0x9A00 0x00CF
Endianness trap. .word 0x9A00 emits 00 then 9A. This means the bytes in the access byte (offset +5 above) come out 9A — correct. But your eyes need to read the hex as 9A, not 00 9A. The .word encoding is little-endian; the segment descriptor byte layout is not.

Each Descriptor, Decoded

Every 8-byte segment descriptor has this structure (Intel SDM Vol. 3A, §3.4.5):

Bit:  7    6    5    4    3    2    1    0
      ┌────┬────┬────┬────┬────┬────┬────┬────┐
  +5  │ G  │ D/B│ L  │AVL │     Limit[19:16] │    Flags + Limit high
      ├────┼────┼────┼────┼────┼────┼────┼────┤
  +4  │ P  │ DPL│ DPL│ S  │ E  │ DC │ RW │ A  │    Access Byte
      └────┴────┴────┴────┴────┴────┴────┴────┘

Decoding each of the four GDT entries in bts_dsk.S:

Entry 0: Null Descriptor (selector 0x00)

    .word 0x0000, 0x0000, 0x0000, 0x0000

All zeros. Required by the x86 architecture — loading SS with a null selector causes a fault. Used as a sentinel for unused slots.

Entry 1: 32-bit Code — selector 0x08

    .word 0xFFFF, 0x0000, 0x9A00, 0x00CF
ByteValueFields
[1:0]0xFFFFLimit[15:0] = 0xFFFFF (with G=1, this becomes 4GB)
[3:2]0x0000Base[15:0] = 0
+40x00Base[23:16] = 0
+50x9A100 10 10 10 — P=1 (present), DPL=0 (ring 0), S=1 (code/data), E=1 (code), C=0, R=1 (readable), A=0
+60x00Base[31:24] = 0
+70xCF1100 1111 — G=1 (page granularity: limit × 4KB), D/B=1 (32-bit), L=0, AVL=0, limit[19:16] = 0xF

Combined: 4GB flat code segment, ring 0, 32-bit, base 0.

Entry 2: 32-bit Data — selector 0x10

    .word 0xFFFF, 0x0000, 0x9200, 0x00CF
ByteValueFields
+50x921001 0010 — P=1, DPL=0, S=1, E=0 (data), DC=0, W=1 (writable), A=0
+70xCFSame as entry 1

The only difference from entry 1 is the access byte: 0x9A (code) vs 0x92 (data). Code segments are readable; data segments are writable. Both cover the same 4GB flat space.

Entry 3: 16-bit Code — selector 0x18

    .word 0xFFFF, 0x0000, 0x9A06, 0x008F
ByteValueFields
+50x9ASame as entry 1 (code, ring 0, readable)
[3:2]0x0006Base[15:0] = 0x0006
+40x00Base[23:16] = 0
+60x00Base[31:24] = 0
+70x8F1000 1111 — G=1, D/B=0 (16-bit), L=0, AVL=0, limit[19:16] = 0xF

Key differences from entry 1:

  • Base = 0x60000 — this segment starts at physical address 0x60000, not 0
  • D/B = 0 — 16-bit default operand/address size. This is how you call back into real-mode BIOS from protected mode: far-jump into this segment, set the CPU to 16-bit mode, then execute int 0x10 etc.
  • Limit = 0xFFFFF × 4KB = 4GB (same as the others)
The 16-bit code segment enables the PICOS BIOS call path. The kernel switches to the 0x18 selector (which has 16-bit default operand size), makes a BIOS call via int, then switches back. This is what powers src/kernel/BIOS.java — it's how PicOS writes to the screen before it has its own graphics driver.

How ptrgdt Feeds LGDT

ptrgdt:
    .word endgdt - mygdt    # limit = 32 bytes (8 × 4 entries)
    .long mygdt              # linear address of GDT base

lgdt m takes a 6-byte memory operand: 2 bytes of limit, 4 bytes of base address. That's exactly what ptrgdt provides. The limit is "size in bytes minus 1" — here, 32 bytes, which is 32 - 1 = 31 but endgdt - mygdt gives 32. Actually:

0x0020 = 32 bytes
┌──────┬────────────────┐
│0x0020│ 0x00000038     │
└──────┴────────────────┘
 limit   base address
Intel says the limit field should be one less than the size (i.e., the last valid byte offset). But endgdt - mygdt here equals 32, which is the size, not the limit. On real CPUs, the LGDT instruction treats the limit as the last accessible byte offset, so this is actually off-by-one. Many bootloaders do this and it works because the CPU doesn't check the limit when loading the GDT itself. You wouldn't want to copy this in production.

The Selector Encoding

Segment selectors in bts_dsk.S:

Selector valueIndexRPLTIReferences
0x000810GDT32-bit code segment
0x001020GDT32-bit data segment
0x001830GDT16-bit code segment

Selector bits: 0x0008 = 0000 0000 0000 1000. The bottom 3 bits are RPL (0) + TI (0 = GDT). The remaining bits are the index (1). Each entry is 8 bytes, so selector = index × 8.

Q1. If you added a fifth GDT entry at offset 32 (0x20), what selector value would reference it?
0x0020
0x0028
0x0024
Index 4 × 8 = 0x20. But that's the byte offset of the entry in the GDT, not the selector. Index 4 in selector format: 4 << 3 | 0 (RPL) | 0 (GDT) = 0x20. So 0x0020 is correct.
Q2. What happens if you try to mov ds, 0x0000 (the null selector)?
It loads 0x0000 into DS successfully but the next access faults.
It causes a #GP (general protection fault) immediately.
It succeeds and DS behaves like a flat segment.
On x86, loading a null selector into CS or SS causes an immediate #GP. Loading into DS/ES/FS/GS succeeds, but any subsequent memory access through that segment raises a #GP. The null descriptor is a trap sentinel, not a usable segment.

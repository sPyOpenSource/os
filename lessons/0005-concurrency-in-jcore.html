Concurrency in JCore: Your synchronized Is a No-op

Lesson 5 of the Java Internals series. Mission | Previous: File System

You already know Java concurrency. That knowledge is actively wrong here. In this codebase, 283 synchronized modifiers across 49 files provide exactly zero mutual exclusion. This lesson is about what replaces them.

The Three Things That Don't Work

You writeWhat actually happens
synchronized vm_monitorenter prints "MONTITORENTER" and returns — src/core/vmsupport.c:398
wait() / notify() sys_panic("not implemented") — the whole kernel dies — src/Interface/zero_object.c:55

Trap. src/org/jnode/driver/bus/usb/spi/AbstractUSBRequest.java:89 is a synchronized void waitUntilComplete(long timeout). It compiles, it looks correct, and it provides no exclusion whatsoever.

This isn't a missing feature — it's a deliberate design choice. JX puts blocking behind the Java line, in the kernel, reachable only through portals. Java code is meant to stay non-blocking and reactive.

The Scheduler You're Actually Running On

Before reaching for any lock, you need to know what can preempt you. From settings.makefile:

line 40   #DEFINES += -DSMP          <- OFF: single CPU
line 41   #DEFINES += -DJAVASCHEDULER <- OFF
line 45   DEFINES  += -DTIMER_HZ=10  <- 100Hz preemption tick
line 52   DEFINES  += -DSCHED_GLOBAL_RR
line 53   DEFINES  += -DSCHED_LOCAL_RR

So: one CPU, a 100 Hz timer interrupt, and a two-level round-robin. The global level cycles domains; each domain's local level cycles its threads. There's a lesson here about verifying claims against the build rather than trusting names.

The Replacement for synchronized

Every working primitive lives in jx.zero, the portal interface package (../../Zero/src/jx/zero/). You get them by name lookup, same as every kernel service:

static CPUManager cpuManager = (CPUManager) InitialNaming.getInitialNaming().lookup("CPUManager");
static Scheduler  scheduler  = (Scheduler)  InitialNaming.getInitialNaming().lookup("Scheduler");

Now watch how JCore builds a mutex from scratch, in src/jx/synch/mutex/BlockingLockImpl.java — a real file in this repo:

public void lock() {
    CPUState mythread = cpuManager.getCPUState();
    for(;;) {
        scheduler.disableThreadSwitching();   // no preemption from here on
        if (owner==null) {
            owner = mythread;                 // test-and-set, now untearable
            scheduler.enableThreadSwitching();
            return;
        } else {
            waiting.enqueue(mythread);        // else get in line
            scheduler.blockAndEnableThreadSwitching();
        }
    }
}

public void unlock() {
    scheduler.disableThreadSwitching();
    CPUState next = waiting.dequeue();
    if (next != null) {
        owner = next;
        cpuManager.unblock(next);            // hand ownership over directly
    } else {
        owner = null;
    }
    scheduler.enableThreadSwitching();
}

The trick is that disableThreadSwitching() makes the test-and-set indivisible. Without it, your thread could be preempted between reading owner and writing it. That single primitive is the foundation.

The general pattern. disableThreadSwitching() → do the tiny critical bit → enableThreadSwitching(). It's JCore's equivalent of "keep the critical section short."

The Replacement for wait / notify

That was a mutex. A condition variable is AtomicVariable. Look at how a blocking queue uses it — src/jx/synch/blocking/Queue.java, in full:

class Node {
    Object value;
    AtomicVariable next = cpuManager.getAtomicVariable();
}

public void enqueue(Object value) {
    Node node = new Node();
    node.value = value;
    node.next.set(null);
    tail.next.atomicUpdateUnblock(node, consumer);   // set pointer AND wake waiter
    tail = node;
}

public Object dequeue() {
    Node ret = head;
    head.next.blockIfEqual(null);                   // sleep until non-null
    head = (Node)head.next.get();
    return head.value;
}

Read the elegance: each link in the queue is an AtomicVariable, so "the next element exists" and "wake the consumer" are the same operation. No lost-wakeup window, because there is no gap between the check and the set.

The author credits Massalin & Pu's synthesis-kernel work in the file header — this is wait-free synchronization, inherited deliberately.

What Replaces volatile

There's no Java Memory Model here, and volatile buys you nothing. Visibility comes from the kernel instead. Look at the native AtomicVariable (src/Interface/zero_AtomicVariable.c:49):

void atomicvariable_blockIfEqual(AtomicVariableProxy * self, ObjectDesc * test)
{
    DISABLE_IRQ;                        // <- interrupts off: nothing else runs

    if (self->value == test) {
        ThreadDesc *thread = curthr();
        self->blockedThread = thread;
        threadblock();
    }
    RESTORE_IRQ;
}

DISABLE_IRQ wraps the check and the block. On a single CPU that makes check-then-act genuinely atomic, and it's why you never need a fence. Interrupts-off is JCore's barrier.

Read Chapter 7, §7.4 "Concurrency control" (p. 80). It is two pages, and it is the design rationale for everything on this page. Chapter 7 §7.2 also covers the scheduler configurations you'll see named in settings.makefile.

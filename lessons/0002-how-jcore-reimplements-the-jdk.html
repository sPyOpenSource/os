How JCore Reimplements the JDK

Lesson 2 of the Java Internals series. Mission | Previous: Class Loading

JCore doesn't run on a standard JVM. It ships its own version of java.lang.*, java.io.*, java.util.* — roughly 300 classes across 18 packages. The implementation differs from HotSpot's JDK in three deep architectural ways.

1. No JNI — Service Lookup Instead

A standard JDK uses native methods to call into the JVM's C++ internals. JCore has zero native methods. Instead, kernel services are looked up at runtime through InitialNaming:

// Standard JDK: native method calls into JVM C++ code
public static native long currentTimeMillis();

// JCore: service lookup from the kernel naming service
Clock clock = (Clock) InitialNaming.getInitialNaming().lookup("Clock");
clock.getTimeInMillis();

This is used everywhere — System.java (line 29):

DebugChannel dc = (DebugChannel)
    InitialNaming.getInitialNaming().lookup("DebugChannel0");
System.out = new PrintStream(new DebugOutputStream(dc));

2. java.lang.Object Is a Skeleton

Every method in Object.java (src/java/lang/Object.java:3) throws an error:

public class Object {
    public    final Class   getClass() {throw new Error("Object method not implemented");}
    public          int     hashCode() {throw new Error("Object method not implemented");}
    public    final void    wait()     {throw new Error("Object method not implemented");}
    public          String  toString() {throw new Error("Object method not implemented");}
    public          boolean equals(Object obj) {throw new Error("Object method not implemented");}
    // ... all 11 methods are the same
}

This isn't a bug — it's by design. The AOT compiler (ByteCodeTranslater) is expected to replace these method bodies with native implementations during compilation to .jll format. The .java file is a specification/skeleton, not the real implementation.

3. Class.forName() Talks to the Kernel, Not the Classpath

Standard JDK: Class.forName() uses the classpath, URLClassLoaders, and a delegation hierarchy.

JCore (src/java/lang/Class.java):

static CPUManager cpuManager = (CPUManager)
    InitialNaming.getInitialNaming().lookup("CPUManager");

public static Class forName(String className) throws ClassNotFoundException {
    return cpuManager.getClass(className);  // kernel call
}

Each Class object wraps a kernel VMClass handle:

public final class Class<T> {
    private VMClass vmclass;   // kernel-level class representation
    long classHandle;
    // ...
}

What This Means

Three patterns replaced the standard JDK's architecture:

Standard JDKJCore JDK
native methods + JNIInitialNaming.lookup() service calls
JVM-built Object methodsAOT compiler replaces skeleton bodies
ClassLoader + classpathCPUManager.getClass() kernel bridge

This is also why reflection is mostly broken — Method.invoke(), Field.get(), and Constructor.newInstance() all throw Error("NOT IMPLEMENTED"). The AOT compiler doesn't need runtime reflection; it resolves everything at compile time.

Primary source: src/java/lang/Object.java, src/java/lang/Class.java, and src/java/lang/System.java — read them side by side with a standard JDK's equivalents.

Quiz

1. What replaces JNI native methods in JCore?

Reveal answer

InitialNaming.getInitialNaming().lookup("ServiceName") — kernel service lookup.

2. Why does Object.hashCode() throw Error in the source?

Reveal answer

The method bodies are skeletons; the AOT compiler replaces them during .class → .jll compilation.

3. How does Class.forName("java.lang.String") work differently from a standard JVM?

Reveal answer

It calls cpuManager.get(className) — a kernel service call — instead of a classpath-based ClassLoader chain.

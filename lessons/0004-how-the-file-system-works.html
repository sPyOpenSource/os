How the File System Works in JCore OS

Lesson 4 of the Java Internals series. Mission | Previous: 32-bit vs 64-bit

JCore OS has two file systems: a simple in-memory one for boot, and a Unix-like one for runtime. Let's trace both.

BootFS — The Boot File System

When the kernel starts, it loads essential files into memory. These are accessed through BootFS (src/jx/zero/BootFS.java):

public interface BootFS extends Portal {
    boolean lookup(String filename);
    ReadOnlyMemory getFile(String filename);
    Memory getReadWriteFile(String filename);
}

DomainStarter.java (src/jx/zero/DomainStarter.java) uses BootFS to load libraries when creating new domains:

bootfs = (BootFS)naming.lookup("BootFS");

// Check if compiled .jll exists
if (bootfs.lookup("mylib.jll")) {
    libData = bootfs.getReadWriteFile("mylib.jll");
} else {
    // Check if source .zip exists, compile it
    if (bootfs.lookup("mylib.zip")) {
        onc.translate("mylib.zip", "mylib.jll");
    }
}

BootFS stores: compiled libraries (.jll), source archives (.zip), and compiler support files. It's a flat namespace — no directories, just filenames.

The Runtime FS — Unix-like Operations

For actual file I/O, JCore uses a Unix-like FS interface (src/jx/fs/). The FS portal provides standard operations:

FS fs = (FS)InitialNaming.getInitialNaming().lookup("FS");

fs.mkdir("/home", 0755);
fs.create("/home/user/test.txt", 0644);
fs.write("/home/user/test.txt", data, 0, data.length());

Node node = fs.lookup("/home/user/test.txt");
int size = node.getLength();

String[] entries = fs.readdirNames("/home");

The Three-Interface Architecture

InterfacePackageWhat It Does
FSjx.fsTop-level operations: cd, mkdir, read, write, etc.
Nodejx.fsInode-level operations: permissions, timestamps, data
FileSystemjx.fsDriver-level: init with block device, get root inode

java.io.File delegates to this chain (src/java/io/File.java):

fs = (FS)InitialNaming.getInitialNaming().lookup("FS");
fsobj = fs.lookup(path);
// Then: isFile(), isDirectory(), length(), list() all delegate to fsobj

Who Implements It?

Only one filesystem works today: NFS v2. The implementation lives in src/jx/rpcsvc/nfs2/NFSInode.java — it implements the Node interface over NFS RPC calls. EXT2 support is planned (permission and attribute classes exist) but not functional.

FileSystem (driver)
  → NFSInode (extends InodeImpl)
    → NFS RPC calls
      → Remote NFS server

Key Architectural Points

  • Portal-based — All FS access crosses domain boundaries via portal interfaces (extends Portal)
  • Separation of concerns — FS handles path operations, Node handles inode data, FileSystem handles the driver
  • BootFS vs FS — BootFS is for loading code at startup; FS is for runtime file I/O
  • NFS-first — The OS is designed to run on a network, with remote filesystems as the primary storage
Primary sources: src/jx/fs/ (interfaces), src/jx/zero/BootFS.java, src/jx/zero/DomainStarter.java, and src/java/io/File.java. See also the FS Interfaces Reference.

Quiz

1. What does BootFS store?

Reveal answer

Compiled libraries (.jll), source archives (.zip), and compiler support files — loaded at boot time into memory.

2. How does java.io.File access the kernel filesystem?

Reveal answer

InitialNaming.getInitialNaming().lookup("FS") — the same portal lookup pattern used everywhere in JCore.

3. What is the only working filesystem implementation?

Reveal answer

NFS v2 — implemented in NFSInode.java via RPC calls to a remote server.

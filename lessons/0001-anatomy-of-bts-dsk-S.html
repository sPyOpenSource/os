Lesson 1: Anatomy of bts_dsk.S

The boot boundary — where PicOS wakes up

bts_dsk.S is the first code that runs when PicOS boots. It lives in the first 512 bytes of the floppy disk image — the boot sector. The BIOS loads it to address 0x7C00 and jumps there in 16-bit real mode. From that tiny footprint, this file must:

  1. Set up the CPU so it can address all of memory (A20 gate)
  2. Switch to 32-bit protected mode
  3. Jump into the PicOS Java runtime

As of my most recent change, it also supports a second entry path: Multiboot2, so GRUB can load PicOS directly. Let's walk through it phase by phase.

Phase 0: The Multiboot2 Header

_start:
    jmp entry_detect

    .balign 8
multiboot2_header:
    .long 0xE85250D6         # magic
    .long 0                  # architecture (i386)
    .long header_len         # header length (24)
    .long checksum           # -(magic + 0 + 24) = 0x17ADAF12
    .word 0                  # end tag type
    .word 0                  # end tag flags
    .long 8                  # end tag size

The very first instruction is jmp entry_detect (2 bytes, assembles to EB 1E). This jumps over the multiboot2 header, which GRUB scans for in the first 32KB of the image. The header is padded to 8-byte alignment with .balign 8.

Why 8-byte alignment? The Multiboot2 spec requires it. The .balign 8 directive fills with zero bytes up to the next 8-byte boundary.

The checksum is computed so that all four 32-bit fields (magic + architecture + length + checksum) sum to zero when added as unsigned 32-bit integers: 

0xE85250D6 + 0 + 24 + 0x17ADAF12 = 0x1_0000_0000 → 0 mod 2³² ✓

Phase 1: Mode Detection

entry_detect:
    smsw ax
    test al, 1
    jnz mb2_entry

This is the clever bit. The smsw (Store Machine Status Word) instruction reads CR0 into ax (16-bit mode) or eax (32-bit mode). Bit 0 of CR0 is the Protection Enable (PE) bit.

Boot pathCPU mode at entryCR0.PEResult
Legacy BIOS16-bit real mode0Fall through to legacy code
GRUB (Multiboot2)32-bit protected mode1Jump to mb2_entry
The byte encoding 0F 01 E0 for smsw ax (in .code16) decodes the same way in 32-bit mode — as smsw eax. Either way, test al, 1 checks the PE bit. The encoding is mode-agnostic.

Phase 2: Legacy BIOS Boot (16-bit)

PIdest:     .long 0
PICDAddr:   .long 0
PIExAddr:   .long 0

These three dword variables are placeholders. The PicOS build tool (compile / BootOut) patches them via bootconf.lin with the real addresses: where the Java image was loaded, its class descriptor, and the entry method. 

mygdt:
    .word 0x0000, 0x0000, 0x0000, 0x0000   # null
    .word 0xFFFF, 0x0000, 0x9A00, 0x00CF   # 4GB 32-bit code
    .word 0xFFFF, 0x0000, 0x9200, 0x00CF   # 4GB 32-bit data
    .word 0xFFFF, 0x0000, 0x9A06, 0x008F   # 4GB 16-bit code at 0x60000

The Global Descriptor Table defines four segments, each 4GB flat:

SelectorTypeBaseLimitFlags
0x00Null——Mandatory
0x0832-bit code04GBPresent, DPL=0, code, 32-bit
0x1032-bit data04GBPresent, DPL=0, R/W
0x1816-bit code0x600004GBPresent, DPL=0, 16-bit

The fourth descriptor (16-bit code at 0x60000) exists so the kernel can call back into real-mode BIOS interrupts. The ptrgdt structure holds the limit and linear address that lgdt needs: 

ptrgdt:
    .word endgdt - mygdt    # limit = GDT size in bytes
    .long mygdt              # linear address of GDT

The A20 Gate

    mov al, 'A'
    call PrintChar          # print 'A' so we know we got here
    call waitKeyboard
    mov al, 0xD1
    out 0x64, al             # command: write to keyboard output port
    call waitKeyboard
    mov al, 0xDF
    out 0x60, al             # set A20 bit

On 8086-compatible CPUs, address line A20 was tied low for compatibility. 0xDF written to port 0x60 enables it, giving access to the full 32-bit address space. The 'A' character signals progress.

Protected Mode: The Two-Step Dance

    lgdt [ptrgdt]            # load our GDT
    mov eax, cr0
    or al, 1
    mov cr0, eax             # enter protected mode
    mov dx, 0x10
    mov fs, dx               # load a big-flat data selector into FS
    dec ax
    mov cr0, eax             # back to real mode
Why enter protected mode and immediately leave? The CPU loads segment descriptor caches only when a segment register is reloaded. The BIOS sets CS, DS, ES, SS with limits of 64KB. By briefly entering protected mode and loading FS with the 4GB data selector, FS now caches a 4GB limit — and this cache persists after switching back to real mode. This gives the boot code a "big flat" segment (FS) to access memory beyond 1MB.

Phase 3: Call Into Java

CallJava:
    mov al, 'P'
    call PrintChar           # print 'P' for Protected Mode
    lgdt [ptrgdt]            # reload GDT
    mov eax, cr0
    or al, 1
    mov cr0, eax             # enter protected mode for real this time

    .byte 0xEA               # far jump opcode
    .long doit                # 32-bit offset
    .word 0x0008             # code selector (GDT entry 1)

The 0xEA far jump reloads CS with the 32-bit code segment (0x08) and lands at doit. This is not a simple jmp doit — only a far jump can change CS and thus the execution mode. 

doit:
    mov dx, 0x10
    mov ds, dx; mov es, dx; mov fs, dx; mov gs, dx; mov ss, dx
    mov esp, INITSTACK        # stack at 0x9BFFC
    mov edi, [PICDAddr]       # class descriptor
    mov eax, [PIExAddr]       # method address
    call eax                  # jump into Java!
Ready:
    jmp Ready

Segments are reloaded with the 32-bit data selector, the stack is set, and then the two patched-in values direct execution into the Java runtime. The call eax is an indirect call — the address was computed by the PicOS build tool and written into PIExAddr.

Phase 4: Multiboot2/GRUB Entry

mb2_entry:                   # entered via GRUB, already in 32-bit PM
    lgdt [ptrgdt]
    mov dx, 0x10
    mov ds, dx; mov es, dx; mov fs, dx; mov gs, dx; mov ss, dx
    mov esp, INITSTACK
    mov edi, [PICDAddr]
    mov eax, [PIExAddr]
    call eax
    jmp Ready

When GRUB boots PicOS via Multiboot2, the processor is already in 32-bit protected mode with A20 enabled. The mb2_entry path skips all the real-mode setup, reloads our own GDT (GRUB provides one, but we want the 16-bit code segment at 0x18), and jumps straight to Java.

Check Your Understanding

Q1. Why does the boot sector need two entry paths?
Legacy BIOS enters in 16-bit real mode; GRUB enters in 32-bit protected mode. They need different setup.
One path is for floppy boot, the other for CD-ROM boot.
The second path is a fallback if A20 gate fails.
The correct answer is the first one. The smsw detection at entry_detect branches based on CR0.PE, which tells us which bootloader loaded us.
Q2. What does the brief protected-mode switch early in the legacy path accomplish?
It loads the GDT so the GDT is in memory.
It loads FS with a segment descriptor that caches a 4GB limit, which persists after returning to real mode.
It tests whether the CPU supports protected mode.
The FS register caches the 4GB segment limit (selector 0x10), giving the real-mode code full memory access. See the "unreal mode" trick in OSDev.
Q3. Why is 0xEA (far jump) used instead of a regular jmp to reach doit?
Because doit is too far away for a short jump.
A far jump reloads CS, which is required to switch from 16-bit to 32-bit execution mode.
Because the assembler doesn't support jmp doit across .code16/.code32 boundaries.
Only a far jump (opcode 0xEA) changes CS. Changing CS is what actually switches the default operand/address size from 16-bit to 32-bit. A near jump (0xE9) only changes EIP and keeps CS unchanged.
